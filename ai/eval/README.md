# 관제 보조 평가 하네스

품질을 **숫자로 증명**하는 자리다. 시트 "모델 적용 3단계" 근거가 여기서 나온다.

## 왜 만들었나

같은 반 다른 팀이 "자체 평가 하네스로 52상황 × 3회 측정, 정확도 0.85 → 1.0"으로 3단계를
받았다. 큰 모델이 아니라 **케이스 단위 재측정 구조**가 점수를 만들었다.

⭐ 그리고 우리 최대 약점인 **데이터 활용 0단계**를 이걸로 메운다. 게이트 기록을 층으로
갈라 골든셋을 만들면 그 설계가 곧 샘플링 전략이라, 시트 3단계 문구 "자체 데이터 수집,
샘플링 최적화"의 뒤쪽 절반이 채워진다.

## ⭐ 사람 라벨이 0이다

DB 집계가 그대로 정답이라 채점이 전부 자동이다. 그래서 하루 만에 세울 수 있었고,
자료가 바뀌어도 다시 뽑기만 하면 된다.

## 돌리는 법

```bash
# EC2 컨테이너 안에서 (실 llama-server 를 부른다)
python -m ai.eval.runner                  # 65벌 × 3회 = 195호출
python -m ai.eval.runner --repeat 5
python -m ai.eval.runner --kind 로봇      # 한 층만
python -m ai.eval.runner --tag q6         # 결과 파일에 이름표
```

골든셋은 16 → 30 → 40 → 45 → 65벌로 늘려 왔다(2026-08-08 기준 65벌). 40벌 시절 120호출이
8~10분이었으니 195호출은 그만큼 더 걸린다. 돌리기 전에 **배포 일정과 겹치는지부터 봐라** —
아래 함정 절의 첫 항목이 그 이야기다.

⚠ **컨테이너 rootfs 가 read-only 다.** 파일을 못 넣으니 `docker exec ... python -c` 로
base64 를 풀어 `/tmp` 에 쓴 뒤 돌린다. 방법은 인계 문서 0-2절에 있다.

### ⛔ 밟은 함정 여덟 (다시 밟기 쉬운 자리)

**돌리는 중에 dev 로 병합하지 마라.** 젠킨스가 컨테이너를 갈면 `/tmp` 가 날아가 실측이
통째로 사라진다. 90호출을 8분 걸려 돌던 것이 흔적도 없이 없어졌다.

**`docker exec -d` 로 `cat > … &` 를 한 줄에 쓰면 stdin 이 끊겨 0바이트 파일이 된다.**
파일 넣기와 띄우기를 두 단계로 갈라라.

```bash
sudo docker exec -i c207-backend sh -c "cat > /tmp/ev_all.py" < /tmp/ev_all.py
sudo docker exec -d -w /app c207-backend sh -c "python -u /tmp/ev_all.py > /tmp/ev.log 2>&1"
```

**base64 를 환경변수로 넘기면 길이 때문에 조용히 실패한다.** 파일로 넣어라.

**`line_buffering=True` 가 없으면 진행이 하나도 안 보인다.** 새로 만든 `TextIOWrapper` 는
`python -u` 와 무관하게 버퍼링돼서, 8분짜리를 중간에 죽이면 버퍼가 통째로 날아간다.
화면이 비어 있는 것을 "안 도는 것"으로 오판하기 딱 좋다.

**결과 파일을 컨테이너 `/tmp` 에 두지 마라. 2026-08-07 하루에 세 번 밟았다.** 배포가 한 번
돌면 컨테이너가 갈리고 `/tmp` 는 빈다. 위 항목이 "돌리는 중"의 이야기라면 이건 **다 돌고
난 뒤**의 이야기다 — 다 끝난 실측도 가져오기 전에 사라진다. 끝나자마자 호스트로 빼라.

```bash
sudo docker cp c207-backend:/tmp/ev_all.json ~/ev/    # 돌자마자 꺼낸다
```

**출력을 `tail` 로 자르면 총계가 밀려난다.** 러너는 케이스 줄을 다 찍고 나서 `====` 아래에
전체 통과율·층별을 찍는데, 실패한 케이스가 있으면 사유·문장까지 두 줄씩 더 붙는다. 그래서
`tail -20` 같은 고정 줄수로는 판마다 다른 자리가 잘린다. **`====` 부터 끝까지**를 잡아라.

```bash
sed -n '/^===/,$p' /tmp/ev.log        # 총계 절만
```

**배포 전 코드를 얹어 잴 때는 얹을 모듈 목록이 곧 측정의 신뢰도다.** 병합 전 수리를 재려고
호스트 파일을 컨테이너에 밀어 넣고 돌리는 구조인데, **한 모듈을 빠뜨리면 그 수리는 안 실린
채로 점수만 나온다.** 오늘 `guards.py` 를 빠뜨려 계약 숫자 예외가 안 실린 판을 그대로 읽을
뻔했다. 손댄 파일 목록과 얹은 파일 목록을 **눈으로 대조하고 나서** 러너를 눌러라.

**상한을 걸어 놓고 지연을 재면 상한에서 잘린 값만 보인다.** 읽기 상한이 8초일 때 재면 8초
넘는 답이 전부 8초로 접혀 "최대 8초"라는 가짜 분포가 나온다. **상한을 풀고 재야** 진짜
꼬리가 보인다 — 그렇게 다시 재서 최대 9.82초가 나왔고, 그 값이 상한을 12초로 올린 근거다.

## 무엇을 재나 — 축 여섯

| 축 | 무엇 | 왜 |
| --- | --- | --- |
| 숫자 **재현율** | 사실에 있는 핵심 수를 답이 빠뜨렸나 | ⚠ 이 축이 없으면 **두루뭉술하게 답해도 만점**이다 |
| 숫자 **정밀도** | 답에 있는데 사실에 없는 수가 있나 | 지어내기·직접 계산 |
| 용어 | 화면 표기 정본대로 썼나 | "미태깅"·"빔 미완" 이 나오면 실패 |
| 거절 | 도메인 밖만 거절했나 | 관제 질문을 거절하면 실패 |
| 형식 | 길이·문단·한국어 순도 | 상한 400자(56벌)·300자(9벌) · 한자 0 |
| 지연 | 몇 초 걸리나 | 중앙값으로 본다 |

⚠ 문단 수(`min_paragraphs`)는 **65벌 중 두 벌에만 걸려 있다**(2026-08-08에 한 벌을 더했다).
형식 축을 "문단까지 본다"로 읽으면 여전히 과대평가다. 대부분의 케이스에서 형식은 사실상
길이와 한국어 순도 둘이다.

## ⭐ 실서비스와 같은 경로·같은 잣대로 잰다 (2026-08-07에 넷을 고쳤다)

하네스가 실서비스와 다르게 재고 있으면 **점수가 아무것도 증명하지 못한다.** 오늘 반대 심문에
그런 자리가 셋 나왔고, 우리 프롬프트가 우리 검사에 걸리는 자리가 하나 더 나왔다.

**① 대화 이력을 태운다.** `routers/assistant.py` 는 `_recent_history` 로 최근 네 메시지를
붙여 부르는데 하네스는 안 붙이고 있었다 — **단일 턴 점수**였던 셈이다. 지금은 케이스에
`history` 를 두면 `pipeline.chat(..., history=...)` 로 그대로 넘긴다. 65벌 중 세 벌이
이력을 쓴다(`chat-이력-그럼어제는`·`chat-이력-인사뒤에`·`chat-이력-인젝션이어받기`).
⚠ 실사용은 "안녕" 다음에 진짜 질문이 오는 흐름이라, 이력 없는 점수는 실물보다 후하다.

**② 폴백을 통과로 안 센다.** `_passed` 가 `generated_by` 를 보게 했다. 예전에는 안 봤는데,
기대 낱말이 비어 있는 케이스는 **LLM 이 죽어도 규칙 문장이 조건을 우연히 만족해 통과로
셌다.** LLM 품질을 재는 하네스가 정작 LLM 을 안 탄 판을 세고 있었던 것이다. 폴백 자체가
결함은 아니지만 여기서는 실패로 세고, 그 `fallback_reason` 이 어디가 깨졌는지 가리킨다.

**③ 거절 판정은 문구 목록이라 원래 샌다.** 모델이 거절하는 말투가 하나가 아니다. 도메인 밖은
"관제 시스템에 대해서만", 제어 요청은 "처리하지 않습니다", 판단 대행은 "대신 판단하지 않"
꼴이다. 새 말투가 나올 때마다 옳은 거절이 실패로 잡히니 목록을 넓히게 되는데 —
**넓힐수록 반대편이 샌다.** 오늘 "알려 드릴 수 없"을 넣었다가 되돌렸다. 그 말은 자료가 없어
못 답할 때도 쓰기 때문이다("…조회 자료에 포함되어 있지 않습니다. 알려 드릴 수 없습니다").
그건 거절이 아니라 **자료 없음을 밝힌 정상 답**인데 가짜 거절이 났다.

> ⭐ 남길 기준 — **그 말이 "안 하겠다"만 뜻하고 "못 한다"로는 안 쓰이는가.**
> 케이스별로 다르면 `refuse_words` 를 그 케이스에 두어 기본 목록을 덮어라.

**④ 숫자 정밀도는 계약 숫자를 예외로 둔다.** 하네스가 `guards.check` 가 아니라
`guards.ungrounded_numbers` 를 직접 부르고 있었다. 우리가 프롬프트에 넣은 설비 번호(게이트
5번·2번 같은 것)를 모델이 답에 적으면 **실서비스는 통과하는데 하네스만 "지어냈다"고 잡았다.**
지금은 `guards.CONTRACT_NUMBERS` 를 빼고 센다 — 실서비스와 같은 잣대다.
⚠ 프롬프트에 새 숫자를 넣을 때는 `CONTRACT_NUMBERS` 도 같이 늘려라. 안 늘리면 그 숫자를
쓴 답이 전부 `number_mismatch` 로 폴백에 떨어지고, 여기서는 폴백이라 실패로 셈된다.

## ⚠ 같은 케이스를 세 번 돌린다

한 번만 재면 **운 좋은 판이 점수가 된다.** 판마다 결과가 갈리는 케이스는 `stable=false`
로 표시하는데, **그 흔들림 자체가 결함**이다.

## ⛔⛔ 한 판으로 단정하지 마라

**케이스 3회는 판 단위 흔들림을 못 잡는다.** 한 판 안에서 같은 케이스를 세 번 돌지만,
그 셋은 **같은 순서·같은 앞선 상태**를 지나며 나온다. 그래서 케이스 안의 흔들림만 보이고,
판을 통째로 다시 돌렸을 때 어디가 바뀌는지는 안 보인다.

2026-08-07에 그대로 밟았다. 37벌 한 판에서 100% 가 나와 그렇게 보고했는데, 40벌로 다시
재니 흔들리는 케이스가 드러났다. **한 판의 100% 는 "100%" 가 아니라 "그 판에서 100%" 다.**

- 수치를 밖으로 내보내기 전에 **판을 한 번 더 돌려라.** 두 판이 같은 이야기를 해야 쓴다.
- 두 판이 갈리면 갈린 케이스 이름을 적어라. 평균으로 뭉개면 그 케이스가 사라진다.
- 100% 가 나와도 러너가 `실패율 95% 상한 3/n` 을 같이 찍는다. **그 상한이 진짜 폭이다.**

## 층을 왜 가르나

층별로 점수를 따로 내야 어디가 약한지 보인다. 그리고 시트 표가 한 줄에서 여러 줄로 넓어진다.

벌 수는 `golden.json` 을 실제로 세어 적는다(아래는 2026-08-08 65벌 기준). 케이스를 더하면
**이 표부터 다시 세라** — 16벌 시절 숫자가 그대로 남아 있던 적이 있다.

| 층 | 벌 | 무엇 |
| --- | --- | --- |
| 질문종류 | 28 | 집계·권한·도메인밖·자료없음·이력·인젝션·인사말 |
| 극단 | 14 | 0건·전부 한쪽·큰 수·앞선 이력. 모델이 무너지는 자리 |
| 결측 | 8 | 칸이 비었을 때 지어내나 |
| 로봇 | 8 | 신선도 판정이 흐르나 |
| 실제 | 7 | 2026-08-06·08-05 DB 실물. 현실성 확인 |
| **합** | **65** | 기능별로는 chat 46 · daily_summary 11 · alert_brief 8 |

거절해야 하는 케이스는 65벌 중 열이다(도메인밖 넷 · 제어 요청 · 개인 지목 셋 · 판단 대행 등).
숫자 축이 실제로 걸린 케이스는 스물여섯이라, 러너의 숫자 점수는 **65벌이 아니라 26벌 기준**이다.

⚠ **2026-08-08에 20벌을 더할 때 층 비중을 같이 고쳤다.** 45벌 시절 질문종류가 24벌(53%)로
절반을 넘었고 통과율이 낮은 층도 거기 하나였다 — 그 층만 더 늘리면 전체 점수가 한 층에
끌려간다. 그래서 얇던 결측(3 → 8)·로봇(4 → 8)을 먼저 채우고 질문종류는 넷만 더해 비중을
43%로 내렸다.

⛔ **`chat-인사-인사뒤집계` 는 지금 실패하는 것이 맞다.** 알려진 구멍을 못박은 회귀 벌이라,
`facts_select` 가 인사 뒤 진짜 질문을 걷어내는 것을 고치기 전까지는 통과하지 않는다. 통과율을
읽을 때 이 한 벌은 **결함이 살아 있다는 표시**로 읽어라.

## 지금 기준선 (2026-08-07 밤 마지막 판)

⚠ **언제 잰 값인지가 수치의 절반이다.** 같은 값이 하루에도 여러 번 바뀌었다 — 프롬프트를
고칠 때마다 통과율이 움직였고, 하네스 자체를 고친 판과 그 전 판은 아예 비교가 안 된다.
아래는 **40벌 × 3회 = 120호출**, 하네스 수리 넷을 다 넣은 뒤의 마지막 판이다.

| 무엇 | 값 |
| --- | --- |
| 전체 통과율 | **98.3% ± 2.3%p** (95%, 케이스 평균 기준) |
| 전판 통과 | 38/40 벌 |
| 흔들린 케이스 | 2벌 (`stable=false`) |
| 지연 중앙값 | 1.8초 |
| 숫자 축 (18벌 기준) | 재현율 100% · 정밀도 100% · F1 100% |
| 층별 | 결측·극단·로봇·실제 100% · 질문종류 97% |

거절 경계는 따로 실측했다 — **답해야 하는 21개를 전부 답했고(거절 0건), 막아야 하는 6개를
전부 거절했다.** 통과율 한 줄보다 이 두 숫자가 "쓸 만한가"를 더 정직하게 말한다.

⚠ 남은 흔들림 둘은 **제어 요청의 새 거절 말투("권한이 없습니다")**와 **사용법 질문이 가끔
폴백으로 떨어지는 것**이다. 앞은 위 ③의 목록 문제이고, 뒤는 모델 쪽 흔들림이다.

## 기대값이 낡는 문제

`실제` 층은 DB 를 그대로 옮긴 값이라 자료가 바뀌면 낡는다. 시각은 `__NOW__`·`__13H_AGO__`
자리표시자로 두어 돌릴 때마다 다시 계산한다 — 절대 시각을 박으면 하루만 지나도
"13시간 전" 이 "37시간 전" 이 된다.

⚠ 자리표시자는 **케이스를 돌리기 직전에 다시 푼다.** 65벌을 미리 다 만들어 두고 순서대로
돌면, 뒤쪽 케이스가 시작할 때 `__NOW__` 는 이미 몇 분 전이라 신선도 문턱(25초)을 넘긴다.

## 결과 파일

`ai/eval/results/MMDD-HHMM-태그.json` 에 케이스별 전판이 남는다. 판마다 **실제 문장**까지
담으므로, 통과율만 보지 말고 실패한 판의 문장을 눈으로 봐라.

## 비교에 쓰는 법

같은 골든셋을 조건만 바꿔 돌리면 before/after 가 나온다.

```
--tag q4-base      Q4_K_M 기준선
--tag q6           Q6_K 로 올린 뒤
--tag temp07       temperature 0.2 → 0.7
```

두 판을 짝지어 비교하는 것은 `compare.py` 다. 케이스별 차이의 평균으로 재니 신뢰구간 둘을
눈으로 겹쳐 보는 것보다 훨씬 좁고 옳다.

```bash
python -m ai.eval.compare results/…-q4.json results/…-q6.json
```

⚠ **한 번에 하나만 바꿔라.** 둘을 같이 바꾸면 어느 쪽이 효과였는지 못 가린다.

⛔ **골든셋이 늘면 예전 판과는 짝이 안 맞는다.** `compare.py` 는 겹치는 케이스만 쓰고 몇 벌을
버렸는지 찍는다. 16벌·30벌·40벌 시절 결과와 지금 65벌 판을 대면 수십 벌이 조용히 빠진 채
"비교"가 되니, **그 경고 줄을 읽고 나서** 숫자를 믿어라.
